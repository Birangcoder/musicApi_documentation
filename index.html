Introduction

Architecture

MusicAPI V2 follows a lightweight, custom MVC-style request flow — no framework, just a router, controllers, models and a thin database layer.

HTTP Request→index.php→Router→Controller→Model→MySQL→JSON

Authentication flow:

Flutter AppPOST /auth/loginMusicAPIValidateMySQLJWT issuedProtected endpoint
Routing note
Locally, /MusicAPI-v2 is stripped before the request reaches the custom router — http://localhost/MusicAPI-v2/songs is matched internally as just songs. Production requests on Render never carry that prefix.

Getting Started

Quick Start

  1. Clone the project 
    git clone YOUR_REPOSITORY_URL
cd MusicAPI-v2
  2. Import the database

    Import database/music_app_v2.sql into MySQL / MariaDB.

  3. Configure secrets

    Set the database and JWT variables shown in Environment Variables. For local dev you can optionally use config/secrets.php — never commit it.

  4. Start Apache/WAMP 
    http://localhost/MusicAPI-v2/
  5. Check API health 
    GET /

    Expected response:

    {
  "success": true,
  "api": "MusicAPI",
  "version": "v1",
  "status": "online"
}
  6. Test songs 
    GET /songs
Getting Started

Local Development

Run the project with WAMP/Apache. The local base URL is:

http://localhost/MusicAPI-v2/

For phone testing, use your computer's LAN IPv4 address instead of localhost:

http://192.168.x.x/MusicAPI-v2/songs
Why? On a phone, localhost means the phone itself. Both devices must be on the same network.

Authentication

JWT Authentication

Login and registration return a JSON Web Token. Protected endpoints require:

Authorization: Bearer YOUR_JWT_TOKEN
AlgorithmHS256
Expiration7 days
Refresh tokenNot implemented
LogoutClient removes token
Token payload
{
  "user_id": 1,
  "email": "user@example.com",
  "iat": 1234567890,
  "exp": 1235172690
}
No refresh route. When a token expires, the client must log in again — JWT_EXPIRE = 60*60*24*7.

Authentication

POST /auth/logout

POST/auth/logoutNo explicit auth

The current implementation returns a successful logout response but does not invalidate JWTs server-side — JWTs are stateless. The Flutter client is responsible for discarding the stored token.

{
  "success": true,
  "message": "Logged out successfully.",
  "data": null
}

Security

  • Passwords are hashed with PASSWORD_BCRYPT.
  • Database operations use prepared statements.
  • JWT uses HS256 with a secret stored outside source control.
  • Never commit passwords, API keys, tokens, .env or config/secrets.php.
  • CORS currently allows all origins (Access-Control-Allow-Origin: *), allowed headers Content-Type / Authorization, and methods GET/POST/PUT/PATCH/DELETE/OPTIONS. OPTIONS requests respond with HTTP 200. For production, consider restricting to trusted client origins.

Deployment

GitHub→Render→Docker→PHP→Aiven MySQL
  1. Push the project to GitHub.
  2. Create a Render Web Service.
  3. Connect the repository and configure Docker deployment.
  4. Add Render environment variables.
  5. Deploy and verify GET / and GET /songs.
  6. Inspect Render logs if an endpoint returns HTTP 500.
Docker

The project ships a Dockerfile based on php:8.3-cli, served with PHP's built-in server:

php -S 0.0.0.0:${PORT:-10000}

Required PHP extensions in the image: mysqli (the app connects with mysqli — this is mandatory), pdo_mysql, zip.

Aiven port: production connectivity uses the configured DB_PORT (documented as 22031) — never assume MySQL's default 3306 for Aiven.
new mysqli(
    DB_HOST,
    DB_USER,
    DB_PASS,
    DB_NAME,
    DB_PORT
);

Troubleshooting

/song → Route not found

/song is not registered. Use /songs for the collection or /songs/{id} for one song.

/songs → HTTP 500

Check, in order: Render environment variables, DB connection, DB_HOST, DB_PORT (not 3306 for Aiven), DB_NAME, DB_USER, DB_PASS, Aiven availability, the PHP mysqli extension, then Render logs.

JWT authentication fails

Verify the same JWT_SECRET is used for creation and validation, and send Authorization: Bearer TOKEN with a space after Bearer.

Local works, Render fails

Compare DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASS, JWT_SECRET, APP_ENV and APP_URL, then inspect Render deployment logs.

Implementation Notes

Current implementation only. Some database tables/controllers exist without active API routes — they're documented here for transparency, not as usable endpoints.
  • not registered  GenreController exists (index/show/search), but genre filtering is currently exposed through GET /tracks?tags=... instead.
  • not registered  artist_follows table exists, but no active follow/unfollow route is registered.
  • not registered  notifications table exists, but no notification API route is registered.
  • not registered  search_history table exists, but no search-history endpoint is exposed.
  • not registered  GET /playlists/{id} is not active despite a show() method existing; use GET /playlists/{id}/tracks.
